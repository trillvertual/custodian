# Модель безопасности

## Границы доверия

Backend контролирует аутентификацию, приглашения и выдачу зашифрованных данных. Он не получает пароли шифрования, PRF-результаты, общий ключ хранилища или открытое содержимое записей. Серверное окружение содержит OAuth credentials, пароль PostgreSQL и первоначальный setup-код; это не ключи расшифровки хранилища.

Все активные администраторы доверенные: они имеют полный доступ к общему хранилищу и могут выгрузить или сохранить его содержимое. Система не предназначена для скрытия секретов от активного участника. Владельцу отдельно доступны управление участниками и журнал. Аудит открытия/копирования фиксирует штатный интерфейс, но не гарантирует регистрацию внештатного локального чтения.

Подтверждение нового публичного ключа проводится владельцем вне приложения: злоумышленник с доступом к серверу может попытаться подменить ключ в UI. Проверка отпечатка через независимый доверенный канал обязательна перед выдачей доступа.

## Примитивы и контексты

- Случайные ключи 256 bit и nonce 192 bit от CSPRNG libsodium.
- AEAD XChaCha20-Poly1305. AAD содержит формат, назначение, vault UUID, record UUID, version и epoch.
- X25519 sealed boxes для передачи общего ключа. Содержимое включает vault UUID и epoch; клиент проверяет их после расшифровки.
- Argon2id 64 MiB / 3 прохода для оболочки приватного ключа пользователя, 128-bit salt.
- PRF 256-bit output оборачивает личный приватный ключ с AAD, включающим user UUID и credential ID. Сервер не получает PRF output; из WebAuthn response он удаляется перед отправкой.
- Опциональный доверенный браузер использует AES-256-GCM WebCrypto: случайный 256-bit неэкспортируемый ключ, nonce 96 bit, tag 128 bit. AAD связывает формат, vault/user/device/credential UUID или ID и публичный личный ключ. Ключ хранится в IndexedDB; зашифрованный личный ключ хранится только на сервере и не сохраняется в browser storage.
- Офлайн-ключ `SVR1.<256-bit random value>` оборачивает общий ключ для определённого vault UUID/epoch.
- Парольный вход использует scrypt N=65536, r=8, p=1 с 128-bit солью и 256-bit результатом.

Криптографические операции использует существующая библиотека libsodium; собственные шифры не реализуются. TOTP реализован на проверенных HMAC/SHA из @noble/hashes и сверяется с полными RFC 6238 test vectors.

## Ограничения E2EE в браузере

Компрометация сервера позволяет изменить клиентский JavaScript и перехватить секреты при следующей разблокировке. Заражённый браузер, расширение, ОС или устройство тоже способны прочитать доступные секреты. CSP, отсутствие сторонних ресурсов и блокировка уменьшают поверхность атаки, но не дают гарантии против такого противника. Развёртывайте проверенный build и контролируйте обновления сервера.

Имена, сайты, заметки, теги и папки зашифрованы. Метаданные пользователей, число записей, версии, время событий и размеры шифртекста видны серверу. Пользовательские ключи best-effort обнуляются; JS strings и копии в памяти браузера невозможно гарантированно стереть. Буфер обмена управляется ОС; копирование явно инициирует пользователь.

Блокировка по бездействию и скрытию вкладки отсутствует. Пользователь блокирует хранилище вручную. При выходе, уходе со страницы и недействительной сессии ключи очищаются; смена epoch требует новой разблокировки. Перезагрузка страницы не сохраняет открытое хранилище: ключи не записываются в постоянное хранилище браузера.

Владелец сервера может удалить данные или откатить БД. AEAD обнаруживает повреждение и подмену контекста, но не обеспечивает независимую защиту от полного согласованного отката сервера. Внешние неизменяемые резервные копии и контроль развёртывания нужны отдельно.

## Регистрация и вход

Публичной регистрации нет. Bootstrap требует случайный setup-код, сериализуется с PostgreSQL advisory lock и закрывается после первого владельца. Приглашения случайные, хранятся как SHA-256 и применяются атомарно один раз. Новый участник не получает записи до подтверждения владельца.

OAuth Authorization Code + S256 PKCE, одноразовый state и независимая cookie привязки к браузеру. Привязка внешнего аккаунта требует существующей свежей сессии. Telegram JWT проверяется по доверенному JWKS, issuer, audience, algorithm, time и обязательному nonce. GitHub account ID используется вместо email/username; access token не сохраняется.

Passkey проверяет challenge, origin, RP ID, credential signature и обязательный user verification. Challenge одноразовый. PRF не является серверным методом авторизации, это только клиентский ключ обёртки.

Токены сессий случайные и хранятся в БД только как SHA-256. Session cookie HttpOnly, Secure в HTTPS, SameSite=Lax, без Domain. Все мутации требуют точного Origin и CSRF token для аутентифицированных запросов. Вход ограничен по частоте, API не кэшируется, логи не сохраняют URL query, cookie, OAuth codes или payload с паролями.

Rate limit хранится в памяти одного процесса. Проект рассчитан на один app-контейнер. За reverse proxy все запросы имеют IP прокси, поэтому лимит общий. `trustProxy` намеренно выключен; если нужен персональный лимит, настройте дополнительный rate limit на доверенном proxy, не включайте доверие ко всем X-Forwarded-For.

## Отзыв и восстановление

Отключение участника транзакционно меняет epoch, все актуальные и исторические ciphertext и sealed boxes активных участников, отзывает сессии отключённого пользователя. Снимок сверяется с текущими версиями и membership, чтобы не затереть параллельные изменения. Старый участник не получает новый ключ, но имеет доступ к любым ранее сохранённым секретам: они должны быть заменены в исходных сервисах.

Админ может заменить свою identity только в свежей аутентифицированной сессии; доступ становится pending, старые PRF wraps и другие сессии отзываются. Владелец сверяет новый fingerprint до повторной выдачи ключа. Rescue владельца требует доступа к БД и подходящего офлайн-ключа. Этот ключ является полномочием на расшифровку всей соответствующей копии хранилища; храните его вне сервера.

Все потерянные unlock-ключи без rescue-ключа или другого активного участника означают потерю расшифровки. Восстановление PostgreSQL само по себе этого не исправляет.

## Эксплуатация

HTTPS обязателен. Не публикуйте PostgreSQL и порт app напрямую; контейнер слушает loopback хоста через Docker port binding. Runtime работает непривилегированным пользователем, файловая система read-only, capabilities удалены. Не выполняйте `docker compose down -v` для production: это удаляет том базы.

План ротации домена, обновления зависимостей, проверки восстановления и внешнего аудита относится к владельцу установки. Размер одного API payload ограничен 8 MiB; очень большие операции ротации требуют увеличения лимита или последующей пакетной реализации. Система не заявляет сертификацию или независимый аудит.

## Единый пароль

Пароль используется в браузере для обёртки личного ключа и отдельно для вычисления привязанного к домену/логину verifier. Сервер получает только verifier; сохранённый verifier не расшифрует личный ключ. Оба KDF используют Argon2id 64 MiB/3 прохода с разными солями. Сервер дополнительно хеширует verifier через scrypt. Пароль/PRF/личный и общий ключи не записываются в БД, localStorage или sessionStorage.

Изменение пароля обновляет hash и identity атомарно, проверяет исходную identity и сохраняет публичный/общий ключи и ciphertext записей. Отключение пароля требует другой PRF-обёртки; удаление последнего рабочего метода запрещено. Внешняя identity и Passkey без PRF не обеспечивают расшифровку и не обходят этот запрет. PRF приходит на сервер только в виде зашифрованной обёртки, без результата расширения.

## Локальные черновики и импорт

Черновики шифруются доменно отделённым ключом BLAKE2b, производным от личного ключа, с привязкой к user/vault/draft ID и ревизии через AAD. IndexedDB и аварийный буфер localStorage содержат только ciphertext и служебные metadata. Общий ключ хранилища не открывает чужие черновики. Смена личного ключа при восстановлении делает их недоступными; серверный backup их не содержит.

CSV/JSON/XML и QR обрабатываются в браузере. DTD и внешние сущности XML отклоняются; размеры файлов, изображений, число записей и зашифрованный request ограничены. Камера запрашивается по действию пользователя, без микрофона. Permissions Policy разрешает камеру только своему origin.

Групповые изменения и импорт применяются под тем же lock, что редактирование и ротация. Права и сессия повторно проверяются после захвата lock. Конфликт любой версии отменяет весь batch. ID запроса связан с участником и hash зашифрованного payload; результат хранится 30 дней. Повтор с другим payload отклоняется.

## Доверенный браузер без PRF

Режим включается самим участником после раскрытия личного ключа и свежего подтверждения Passkey. Он нужен, например, для Passkey из Bitwarden, который подтверждает вход, но не отдаёт PRF-результат. Это изменение модели хранения ключей, а не отключение WebAuthn или серверных прав.

В отдельной IndexedDB `custodian-device-keys` хранится только неэкспортируемый `CryptoKey` AES-256-GCM и контекст браузера. Открытые личный ключ и vault key, пароль и зашифрованная оболочка личного ключа туда не записываются. Сервер получает только оболочку и метаданные; её выдача требует действующей сессии с подтверждением того же credential не старше 60 секунд, активного участника и неизменного личного ключа. Origin и CSRF обязательны. Сохранённая парольная/OAuth-сессия сама по себе не открывает эту оболочку. Добавление доверия требует Passkey-подтверждения не старше 15 минут.

Сессия получает credential ID только после настоящей проверки WebAuthn assertion. Привязка к credential, свежесть, существование сессии и статус участника повторно проверяются внутри транзакции с блокировкой; обычный список браузеров не содержит оболочек. На участника разрешено до 10 браузеров. Отзыв браузера, удаление Passkey и сброс личного ключа запрещают будущие открытия. Парольный вход автоматически не выключается: он остаётся способом настройки нового профиля. Формат записей и rescue-ключей не меняется.

Режим требует доверия к профилю браузера. Неэкспортируемость WebCrypto ограничивает API экспорта, а не делает ключ аппаратным или недоступным владельцу ОС. Заражённое устройство или вредоносное расширение способны перехватить данные. Если сервер подменит клиентский JavaScript, он сможет использовать локальный ключ при открытии страницы; эта модель не равна PRF по защите от подменённого сайта. Отзыв доверия не стирает уже раскрытые данные и не блокирует автоматически открытое хранилище. На общих устройствах этот режим включать нельзя. Серверная резервная копия без браузерного ключа и локальный ключ без серверной оболочки сами по себе личный ключ не раскрывают.

Право получить оболочку одноразовое для каждой Passkey-сессии. Повторный запрос после успешной выдачи требует нового WebAuthn-подтверждения; при потере ответа нужно повторить Passkey, а не вводить мастер-пароль. Неизвестный или устаревший device ID это право не расходует.

Схема разделения хранения опирается на стандартный подход доверенных устройств; её реализация в Custodian не проходила независимый криптографический аудит. Первичные сведения: [Bitwarden trusted devices](https://bitwarden.com/help/about-trusted-devices/), [CryptoKey structured clone в IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm).
